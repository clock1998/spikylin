Pendant que je travaille sur un projet de budget personnel, j'ai rencontré un problème : il est très difficile de catégoriser automatiquement une transaction à partir de sa description. Une description de transaction contient souvent uniquement un nom d'entreprise, et il est difficile de déduire la catégorie budgétaire uniquement à partir de ce nom avec un LLM. Beaucoup de noms d'entreprises ne sont pas représentatifs de leur activité économique, comme Apple. Les noms d'entreprises sont aujourd'hui davantage utilisés comme outil marketing. Le problème devient encore plus important lorsqu'une transaction est effectuée auprès d'une entreprise locale. Par exemple, Kim Phat est une épicerie asiatique qui n'existe qu'au Québec, et son nom ne dit rien sur son activité. De plus, beaucoup de noms d'entreprises au Québec sont en français, ce qui rend la catégorisation automatique encore plus difficile.

Après quelques recherches, plusieurs solutions existent. La plus simple consiste à utiliser un LLM de 70 milliards de paramètres et à espérer qu'il connaisse l'entreprise grâce à ses données d'entraînement. Cependant, cette solution est très coûteuse et peu fiable. Les connaissances d'un LLM dépendent fortement de ses données d'entraînement. Une nouvelle entreprise créée hier n'y figurera pas, donc le LLM ne la connaîtra pas. Cette solution est aussi coûteuse car elle nécessite d'acheter des jetons API auprès de fournisseurs cloud comme OpenAI. La deuxième option consiste à trouver une API publique capable de rechercher une entreprise par son nom et de retourner sa catégorie ou sa description. Après quelques recherches, je n'ai trouvé aucune API publique de ce type. Bien que le gouvernement du Québec propose un site web pour rechercher une entreprise, celui-ci n'est pas exposé sous forme d'API. Il serait toutefois possible de développer un crawler web pour exploiter ce site, mais cela impacterait la vitesse et pourrait poser des problèmes juridiques. Il existe néanmoins une manière d'utiliser l'API Google Maps pour rechercher l'entreprise et filtrer les résultats à l'aide d'un LLM ou simplement d'expressions régulières. La troisième solution consiste à choisir un modèle zero-shot et à utiliser des techniques de SFT pour lui apprendre à reconnaître toutes les entreprises locales. Bien que cette solution nécessite elle aussi des ressources supplémentaires comme un matériel puissant et un jeu de données de haute qualité, elle est tout à fait envisageable. C'est mon plan B, car j'ai peu d'expérience avec le SFT et un bon résultat final n'est donc pas garanti. La dernière solution consiste à utiliser une approche hybride RAG. C'est celle qui demande le moins de ressources tout en pouvant fournir des résultats de haute qualité. J'ai trouvé tous les enregistrements d'entreprises du Québec sur [Donnees Quebec](https://www.donneesquebec.ca/recherche/dataset/registre-des-entreprises). Le jeu de données contient le nom et la description des entreprises. Le plan consiste à retrouver la description d'une entreprise à partir de son nom, puis à l'envoyer à un modèle zero-shot pour catégoriser l'entreprise, et donc la transaction. Je commencerai par effectuer une recherche plein texte sur les noms d'entreprises pour trouver leur description. Si cela ne fonctionne pas à cause de noms masqués ou d'acronymes, je ferai ensuite une recherche sémantique. Une fois le nom trouvé, je récupère la description de l'entreprise. Je peux ensuite effectuer une classification zero-shot qui devrait placer l'entreprise dans une bonne catégorie de budget personnel. La raison pour laquelle je n'étiquette pas chaque activité au moment où je crée les embeddings est que je ne veux pas perdre en flexibilité. Par exemple, si quelqu'un d'autre veut utiliser mon outil, avec le zero-shot il lui suffira de fournir ses propres catégories, même dans d'autres langues.

Pour les entreprises absentes de la base, j'implémenterai une fonctionnalité de repli utilisant un MCP comme Brave Search. Le catégoriseur essaiera alors de catégoriser l'entreprise à partir des résultats de recherche.

Mise à jour 2026-02-14 Changement de stratégie de recherche

Après de nombreux tests, j'ai décidé d'abandonner l'approche consistant à faire de la recherche sémantique sur les noms d'entreprises, car ce n'est ni efficace ni bien adapté au cas d'usage. Sans contexte plus détaillé ou description, il y a très peu de sens sémantique dans les noms d'entreprises. Certes, la recherche sémantique retourne toujours un résultat, mais celui-ci peut être sans rapport avec l'entreprise recherchée. Une recherche plein texte est plus adaptée ici, car j'ai seulement besoin de retrouver les noms d'entreprises qui correspondent au plus grand nombre de mots-clés. En revanche, j'utilise la recherche sémantique ailleurs. J'ai décidé de développer une recherche web de secours au cas où le nom de l'entreprise ne serait pas trouvé dans la base. En réalité, il est fréquent qu'un nom d'entreprise n'apparaisse pas dans ma base, car beaucoup d'entreprises sont internationales, comme Amazon ou Apple.com. Dans ce cas, je recherche l'entreprise avec l'API de Google et j'utilise une recherche sémantique pour filtrer les résultats non pertinents. Cette approche me donne jusqu'à présent les meilleurs résultats.
